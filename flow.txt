 Now let's walk through each stage, point by point, matching the diagram top to bottom.

1. Client → POST /chat
The client already has a thread_id (from a previous /session call) and sends a new message: {"thread_id": "...", "user_input": "give me a hard DSA question"}.

2. compiled_graph.invoke()
FastAPI's chat() function calls compiled_graph.invoke({"user_input": ...}, config={"configurable": {"thread_id": ...}}). Behind the scenes, LangGraph looks up everything already stored for that thread_id (company_name, role, message history) and merges in the one new field you passed — user_input. Nothing you didn't explicitly send gets lost.

3. classifier_node
This runs first, always — it's what START points to. It reads the fresh user_input, asks the LLM which of the four categories it falls into, and writes that label into state['classifier'].

4. The branch point
router_function reads state['classifier'] and returns one of four labels. Your add_conditional_edges mapping then sends execution to exactly one of the four paths — never more than one per request.

5. The four branches themselves

DSA → this box hides more detail than it shows: it's actually reviwer_node → three parallel candidate nodes → picker_node. All of that collapses into final_result by the time it reaches this point.
Behavioral → one direct LLM call, no retrieval needed.
Company research → calls Tavily search first, then feeds those results into the LLM.
Resume gap → calls your FAISS resume_retriever first, then feeds those chunks into the LLM.

Whichever one runs, it writes into the same state['final_result'] key.

6. Convergence → END
No matter which branch ran, they all point to END in your graph. app.invoke() returns the final state dict.

7. Back to the client
chat() pulls result["final_result"] and result["classifier"] out of that dict, wraps them in your ChatResponse Pydantic model, and FastAPI serializes that as the JSON response the client receives.
